Введение 

Преддипломная практика является важным этапом подготовки выпускной квалификационной работы. В период практики студент должен не только закрепить знания, полученные на дисциплинах по программированию, проектированию информационных систем и базам данных, но и показать умение самостоятельно выполнить работу от анализа предметной области до тестирования готового программного продукта. В моём случае тема практики связана с разработкой официального информационного ресурса (сайта) администрации Сергиево‑Посадского городского округа — то есть проекта, который одновременно является продолжением курсовой работы и основой для диплома.

Официальный сайт органа местного самоуправления сегодня — это не «визитка в интернете», а полноценный канал работы с жителями. Через сайт человек может узнать новости, найти документы, посмотреть сведения о руководстве и подразделениях, перейти в разделы «Финансы», «Экология», «Справочная» и подать обращение в электронной форме. Для администрации сайт помогает не терять обращения, фиксировать ответы и в перспективе видеть статистику: какие темы повторяются, где чаще возникают задержки с ответом.

В рамках практики я разрабатывал информационный ресурс, который включает несколько частей. Первая — публичная: страницы с информацией, новости, документы. Вторая — сервисная: личный кабинет гражданина, форма обращения, антикоррупционные сообщения. Третья — служебная: кабинет сотрудника и администратора для обработки обращений, публикации материалов, управления справочниками. Четвёртая — аналитическая: сводные показатели и графики по обращениям. Такое разделение я использовал и в отчёте, потому что оно помогает не смешивать всё в одну «кучу» и понятнее объяснять на защите.

Актуальность темы, на мой взгляд, очевидна из обычной практики. Жителям удобнее отправить обращение через сайт, чем только приходить на личный приём. Сотрудникам администрации нужна единая база, а не разрозненные таблицы и папки. Руководству нужны цифры для решений. Плюс есть требования к доступности сайта для людей с ограничениями по зрению — в проекте реализован режим для слабовидящих, и это отдельно описано в отчёте.

Цель практики: подготовить аналитические материалы для выпускной квалификационной работы и выполнить проектирование и разработку информационного ресурса администрации — от анализа требований до работающего прототипа на Laravel с базой MySQL, модулями обращений, служебных кабинетов и аналитики.

1. Анализ предметной области 

1.1. Сведения об организации 

Перед тем как писать техническую часть, мне нужно было разобраться, для кого вообще делается сайт. Я не работаю в администрации, поэтому опирался на открытые материалы: официальный сайт округа, разделы про структуру органов власти, а также консультации руководителя практики. Смысл в том, что программисту важно понимать не только «какие кнопки нарисовать», но и как в реальности проходит обращение гражданина: куда оно попадает, кто отвечает, какие сроки считаются нормальными.

Сергиево‑Посадский городской округ — муниципальное образование в Московской области. Для жителей сайт — один из основных способов узнать новости, найти телефоны и адреса, скачать документы и подать обращение, не обязательно приезжая лично. Для сотрудников администрации сайт — рабочий инструмент: через служебный раздел видно входящие обращения, можно подготовить ответ и зафиксировать результат в системе. Именно поэтому в проекте есть разделение на «публичную» и «служебную» части — это не усложнение ради усложнения, а отражение реальной работы.

Объектом разработки является официальный веб‑ресурс администрации Сергиево‑Посадского городского округа Московской области. Администрация как орган местного самоуправления решает задачи управления территорией, обеспечения жизнедеятельности, предоставления муниципальных услуг и организации коммуникаций с населением. 

В контексте цифровых сервисов важными направлениями деятельности являются: 

— информационная открытость: публикация новостей, документов, отчётов, сведений о подразделениях и должностных лицах; 

— обратная связь: приём обращений граждан и сообщений по отдельным тематикам (в том числе антикоррупционные обращения); 

— контроль исполнения: соблюдение сроков рассмотрения обращений, фиксация ответов, хранение материалов; 

— аналитическое сопровождение: агрегирование статистики обращений (количество, динамика, структура тем).	 

Организационно работа с обращениями распределяется между профильными подразделениями администрации. Гражданин инициирует обращение через веб‑форму, система фиксирует факт обращения и его классификацию, после чего оно становится доступным сотрудникам для дальнейшего рассмотрения. На уровне информационных потоков это означает последовательность: формирование входных данных → валидация и сохранение записи → передача обращения сотруднику → подготовка ответа с прикреплением материалов (при необходимости) → фиксация результата и обновление статуса для гражданина → включение обращения в статистическую выборку аналитического модуля. 

Нормативная значимость данных процессов обусловливает требования к устойчивости хранения и воспроизводимости результатов. В проекте учитываются принципы минимизации и защиты персональных данных, а также необходимость обеспечения доступности веб‑ресурса для различных категорий пользователей. Поэтому функциональная модель системы опирается на регламентированные сценарии, где критичные действия (отправка обращения, формирование ответа, смена статуса) должны выполняться строго в рамках заданных параметров и фиксироваться в системе. 

Сайт администрации выступает как единая «витрина» информации для граждан и одновременно как рабочий инструмент для сотрудников (служебный кабинет), поскольку обработка обращений является частью постоянной деятельности. 

Для рассматриваемой системы рационально выделить роли: 

— Гость (неавторизованный пользователь): просматривает публичные страницы, новости, документы; не может подать обращение без входа (в целях идентификации и защиты от спама). 

— Пользователь (гражданин): после регистрации и входа подаёт обращение, просматривает свои обращения и ответы, при необходимости редактирует обращение до момента ответа. 

— Сотрудник (staff/employee): имеет доступ к спискам обращений и антикоррупционных сообщений, формирует ответы, видит аналитические показатели. 

— Администратор (admin): управляет пользователями и ролями, настройками справочников (категории проблем), редактирует информационный контент сайта (новости, документы/справочные страницы, элементы карусели) и имеет доступ к расширенной сводке (дашборду). 

 

Такая модель согласуется с реальными процессами: граждане инициируют обращение, сотрудники рассматривают и готовят ответ, администратор поддерживает справочники и распределение прав доступа. 

Для обеспечения управляемости и прослеживаемости процесса рассмотрения обращений в системе фиксируются этапы работы с документом (обращением) и обеспечивается связность информации между инициатором, классификацией проблемы и результатом рассмотрения. С точки зрения информационных потоков это означает, что входные данные, введённые гражданином, должны быть проверены и корректно сохранены, а затем — переданы сотруднику для обработки в унифицированном виде. При формировании ответа важно сохранить неизменность существенных реквизитов обращения после его рассмотрения, что достигается ограничением на редактирование и ведением истории изменения статусов. 

Отдельным важным аспектом выступает соблюдение требований по защите персональных данных: система должна ограничивать доступ к персональным сведениям (только сотрудникам и администратору при необходимости выполнения служебных функций), минимизировать объём данных, который выводится в публичной части, и обеспечивать контроль корректности вводимых значений. В совокупности эти требования определяют архитектуру системы и набор функциональных сценариев, которые должны быть реализованы в проекте. 

Информационный поток “обращение → рассмотрение → результат” должен быть прослеживаемым на всём протяжении процесса. Практически это означает, что при подаче обращения формируется первичная запись с привязкой к выбранной категории проблем, датой создания и набором вложений. Далее обращение поступает в служебный контур, где сотрудники выполняют последовательность операций: проверяют корректность заполнения, при необходимости уточняют классификацию (в рамках допустимых правил), фиксируют дату начала рассмотрения и, по завершении, оформляют ответ. Для руководства и аналитического контура критично наличие временных меток 

Кроме функциональных требований, важны организационные особенности: сотрудники должны иметь удобный интерфейс чтения данных без необходимости “выискивать” информацию в разных разделах, а администратор — инструмент поддержки справочников, чтобы обновления категорий проблем отражались в пользовательских формах без задержек. В системе должны учитываться изменения организационной структуры и состава ролей: при корректном разграничении доступа новые сотрудники могут быть подключены к процессу рассмотрения без изменения структуры данных. 

Таким образом, в рамках преддипломной практики рассматривается не только программная реализация страниц, но и логика управляемого процесса обработки обращений, которая обеспечивает связность информационных данных, воспроизводимость результатов аналитики и прозрачность взаимодействия с гражданами. 

 

 

 

 

 

1.2. Информационная и функциональная структура 

Информационное наполнение сайта делится на несколько групп: Пользовательские данные 

   — учетные записи пользователей; 

   — роли доступа; 

   — учетные данные для аутентификации. 

Контентные данные 

   — новости и статьи (унифицированный механизм разделов/секций); 

   — материалы для главной страницы: изображения и элементы карусели, привязанные к конкретным публикациям/объявлениям; 

   — разделы меню (включая «Документы», «Финансы», «Экология», «Справочная»); 

   — справочные материалы и документы: карточки документов и прикреплённые файлы, обеспечивающие доступ к актуальным сведениям; 

   — справочные сведения и контакты. 

Сервисные данные (обращения) 

   — обращение гражданина: ФИО, контактные сведения, текст обращения, вложение, согласие на обработку персональных данных; 

   — статус обработки: «на рассмотрении» / «ответ получен»; 

   — ответ сотрудника, дата ответа, сотрудник‑исполнитель; 

   — дополнительные материалы по ответу (фото/файлы при необходимости). 

 

Справочники классификации проблем 

   — категории проблем (верхний уровень); 

   — подкатегории (второй уровень); 

   — детальные проблемы (третий уровень). 

Аналитические данные 

   — агрегированные показатели по обращениям и антикоррупционным сообщениям; 

   — динамика по месяцам; 

   — топ‑категории/подкатегории/детали проблем; 

   — метрики SLA (вовремя/просрочено) и среднее время ответа. 

Для корректной работы служебного контура дополнительно выделяются прикладные данные, обеспечивающие целостность процесса рассмотрения: 

— история статусов (логирование изменения этапов обращения) — позволяет восстановить ход работы и объяснить пользователю текущий статус; 

— вложения и материалы (файлы и фотографии) — хранятся с привязкой к обращению/ответу, чтобы данные не терялись при просмотре карточки; 

— расписание обработки — набор дат/состояний, помогающий сотрудникам управлять очередью и контролировать сроки; 

Функционально система разделяется на четыре взаимосвязанных контура. 

Публичный контур (информационный сайт) 

— главная страница с каруселью, блоком новостей и быстрыми ссылками; 

— страницы «Администрация», «Документы», «Финансы», «Экология», «Справочная» и др.; 

— новостной раздел и другие секции статей; 

— футер с правовой информацией и навигацией по основным разделам. 

Пользовательский контур (личные сервисы гражданина) 

— регистрация и авторизация; 

— форма подачи обращения (в том числе прикрепление файлов и согласие на обработку персональных данных); 

— список «Мои обращения» с краткими карточками и статусами; 

— просмотр конкретного обращения и ответа (если ответ дан); 

— редактирование обращения до получения ответа; 

— профиль пользователя, возможность смены пароля. 

Служебный контур (обработка обращений и контента) 

— кабинет сотрудника: список обращений, просмотр карточки обращения, ответ; 

— обработка антикоррупционных сообщений по аналогичному жизненному циклу; 

— управление контентом (публикации новостей/статей, страницы документов и справочных материалов, элементы карусели, вакансии и иные информационные блоки) с поддержкой сценариев создания/редактирования и загрузки файлов;

— расчёт SLA по срокам ответа (на основе параметра окружения, по умолчанию 7 дней); 

— визуализация динамики и структуры тем (графики). 

Чтобы контуры функционировали согласованно, в проекте задаётся единая логика обработки обращения и единый формат хранения справочной информации. Пользовательский контур обеспечивает ввод и наблюдение за статусом обращения. Служебный контур обеспечивает рассмотрение и формирование ответа, при этом классификация проблемы используется как ключевое поле для последующего анализа. Аналитический контур вычисляет показатели (в том числе SLA) на основе статусов и временных меток, поэтому корректность ведения статусов в служебной части напрямую влияет на качество аналитики. 

Типовой жизненный цикл обращения включает следующие стадии: создание (подача гражданином), модерация на уровне корректности ввода и классификации, рассмотрение сотрудником, подготовка ответа и фиксация факта ответа, итоговое отображение результата гражданину и последующее включение обращения в агрегированную статистику. Такое разделение уменьшает логическую связанность между слоями и позволяет в дальнейшем расширять систему

В системе это достигается сочетанием ограничений целостности данных и правил формирования набора доступных значений. 

Отдельно отмечается требование к воспроизводимости: после развёртывания системы справочники категорий и проблем должны быть доступны сразу, поэтому в проекте предусматривается загрузка стартовых данных через сидеры. Это обеспечивает демонстрируемость функционала во время практики и при подготовке к защите.

Для аналитической страницы важны не только показатели “в числах”, но и удобство интерпретации. Поэтому при построении диаграмм учитывается читабельность на разных устройствах: подписи категорий отображаются в виде кратких наименований, при необходимости раскрываемых пользователем. График динамики строится по месяцам и позволяет выявлять периоды роста обращений, после чего сотрудник может выполнить переход в соответствующий разрез списка обращений. 

Разрез “вовремя/просрочено” демонстрирует качество соблюдения сроков. При расчёте доли просрочки используются временные метки создания и факта ответа, а результат агрегируется так, чтобы администратор мог сравнить периоды между собой и оценить эффект от организационных изменений. Такой подход делает аналитику не просто описательной, но и управляемой. 

Аналитика служит прототипом и основой для будущего расширения до уровня “тепловой карты” (например, при добавлении территориальной привязки обращений можно строить карты интенсивности).

— Документы и справочная информация (`documents` и `reference`): страницы предназначены для публикации нормативных актов и материалов общего характера. Они должны поддерживать удобную навигацию и единый стиль представления, чтобы пользователь мог быстро найти нужную информацию до подачи обращения.

— Административный каталог категорий проблем (`admin/problem—categories/index`): страница управления иерархией тем предназначена для поддержки словаря проблем. Через неё администратор включает/отключает элементы, задаёт порядок и обеспечивает корректность связей между уровнями иерархии. 

 

Карточки обращений: 

  — со стороны гражданина (`appeals/show`, `appeals/edit`, `appeals/index`): пользователь получает единый формат отображения данных, видит статус, а редактирование ограничивается рамками регламента;

— Компоненты макета (`layouts/app`, `components/header`): единая шапка обеспечивает идентичные элементы навигации на всех страницах, а также поддерживает адаптивное меню. Это снижает когнитивную нагрузку на пользователя и уменьшает вероятность ошибочной навигации. 

 

— Виджет доступности (`components/accessibility—widget`): компонент должен работать одинаково независимо от страницы, сохранять выбранный режим отображения в рамках пользовательской сессии и обеспечивать предсказуемое изменение визуальных параметров интерфейса. 

 

— Служебная аналитика (`staff/analytics/index`): страница предназначена для сотрудников и администраторов и обеспечивает доступ к KPI, динамике и структуре тем в разрезе категорий проблем. В практическом использовании она выступает инструментом контроля нагрузки и качества обработки обращений, а её представление согласуется с общим дизайнерским стилем сайта и настройками доступности. 

Важно также отметить, что информационная часть сайта включает новостные блоки, разделы документов и справочные страницы. Со стороны администрации предусмотрены интерфейсы редактирования и обновления этого контента: добавление/изменение публикаций, управление вложениями (например, файлами для документов) и поддержка визуальных элементов главной страницы (карусель). В рамках преддипломной практики основное внимание уделяется проектированию и верстке интерфейса для этих сценариев, чтобы обеспечить единый стиль, адаптивность и доступность при дальнейшем наполнении и эксплуатации сайта. 

Дизайн системы выполнен в рамках фирменной стилистики округа: 

— цветовая схема выбрана главой Сергиево‑Посадского городского округа и соответствует утверждённой палитре администрации: основной тёмно‑зелёный (навигация, кнопки, акценты), светлый фон страниц и контрастный акцентный цвет для выделения активных элементов; 

— шрифтовое оформление основано на специально разработанных для округа дизайнерами шрифтах: SK Posad (для заголовков и навигации) и SK Posad Text (для основного текста); 

— единые компоненты интерфейса: фиксированная шапка (header) с адаптивным меню, футер с правовой информацией и ссылками; 

— адаптивность: поддержка мобильных устройств (бургер‑меню, переразмещение блоков); 

— доступность: реализован виджет “версия для слабовидящих” с настройкой шрифта, контрастных схем (белый/чёрный, чёрный/белый, жёлтый/чёрный, чёрный/жёлтый), инверсией, монохромным режимом, отображением фокуса и отключением анимаций. 

Таким образом, система сохраняет единый официальный визуальный стиль и одновременно обеспечивает доступность и удобство для разных категорий пользователей. 

Цветовая идентичность при этом используется как единый “theme—first” принцип: ключевые параметры интерфейса (контраст, фоновые подложки, акцентные элементы и размеры типографики) сведены к согласованным значениям и применяются во всех шаблонах сайта. Это поддерживает узнаваемость ресурса, снижает неоднородность визуального представления и помогает пользователю быстрее ориентироваться в интерфейсе (в том числе при переключении режимов доступности). 

Технически выбранная палитра и типографика реализуются через единые параметры оформления, которые задаются на уровне шаблонов и переиспользуемых компонентов. Такой подход упрощает сопровождение: при необходимости изменить оттенок акцентного цвета (или уточнить толщину/размер шрифта) изменения вносятся в ограниченное число точек и автоматически отражаются на всех страницах, включая публичные и служебные интерфейсы. 

Отдельное внимание уделено визуальному восприятию статусов в карточках обращений. Для этого используется контрастное кодирование: статусы “на рассмотрении”, “ответ получен”, а также служебные индикаторы по срокам SLA представлены в виде устойчивых графических меток (бейджей/лейблов). При переключении режима доступности вид и контраст этих меток должны оставаться различимыми, поэтому при проектировании учитывается не только цвет, но и форму/пиктограммы и текущее значение статуса как текст. 

В рамках адаптивности фиксированная шапка (`header`) переводится в компактный вид для мобильных устройств: меню сворачивается в “бургер”‑структуру, а элементы навигации переразмещаются так, чтобы не создавать горизонтальную прокрутку. Для страниц обращений и аналитики учитывается ограничение ширины экрана: табличные блоки и списки снабжаются переносами и вертикальной структурой, а формы — управляемыми полями с понятной системой подсказок. 

Компонент “версия для слабовидящих” реализует не только смену размера шрифта, но и изменение набора визуальных параметров интерфейса. В отчётной модели выделяются следующие сценарии работы пользователя: 

 

— активирование режима повышенной доступности переводит интерфейс в согласованный набор контрастных схем (например, “белый/чёрный”, “чёрный/белый”, “жёлтый/чёрный”, “чёрный/жёлтый”) и обеспечивает видимый фокус для элементов управления; 

— переключение контрастного режима не должно ломать верстку: блоки остаются в прежних сетках, а текста достаточно для читаемости без “налезания” и обрезки; 

— при отключении анимаций интерфейс перестаёт использовать декоративные движения, но сохраняет функциональную обратную связь (например, подсветку ошибок в формах и смену статусов); 

— при взаимодействии с клавиатурой (tab/shift+tab/enter) пользователь должен получать предсказуемую индикацию текущего фокуса. 

Для формы обращения важна доступность взаимодействия именно на уровне ошибок валидации. Поэтому в интерфейсе закладывается стратегия вывода сообщений: ошибки отображаются рядом с полями, сопровождаются понятным текстом и не зависят исключительно от цветовой индикации. Такой подход улучшает читабельность для пользователей с пониженным зрением и уменьшает вероятность ошибочного заполнения. 

Таким образом, дизайн рассматривается как совокупность визуальных и функциональных требований. Он обеспечивает единообразие муниципального стиля, поддерживает интерактивные сценарии (подача обращения, редактирование до ответа, просмотр карточек и аналитики) и формирует доступную среду для разных категорий пользователей. 

 

 

 

 

 

1.3. Классификация информационных систем  

Разрабатываемая система относится к классу веб‑ориентированных информационных систем муниципального управления, совмещающих функции: 

— информационной системы публикации данных (официальные сведения, новости, документы); 

— сервисной системы обработки обращений (приём, хранение, ответы, статусы); 

— информационно‑аналитической системы поддержки принятия решений (KPI и графики по обращениям). 

По архитектуре система является клиент‑серверной с организацией логики в стиле MVC: 

— Model: модели доменных сущностей (пользователь, обращение, справочники проблем); 

— View: шаблоны интерфейса на Blade; 

— Controller: контроллеры, реализующие бизнес‑логику и обработку запросов. 

По способу использования: 

— много пользовательская; 

— с разграничением доступа на основе ролей; 

— с разделением на публичный и служебный контуры. 

По характеру обрабатываемых данных система работает с персональными данными (ФИО, email, телефон/адрес при наличии), поэтому предъявляются требования к защите данных и ограничению доступа. 

По степени регламентированности и уровню автоматизации система относится к прикладным информационным системам с “процедурной” логикой: пользовательские действия запускают формирование записей, статусные значения меняются при определённых событиях, а аналитика вычисляется на основе временных меток и классификационных связей. Таким образом, система поддерживает не только хранение и отображение данных, но и выполнение последовательности операций в соответствии с регламентом рассмотрения обращений и требованиями по обеспечению официальности результатов. 

Дополнительно важно отметить, что иерархическая классификация проблем реализует структурирование “семантики” обращения. Это позволяет снизить неоднородность текстовых запросов и повысить качество аналитики, поскольку вместо свободного текста используются контролируемые справочные значения. 

 

 

 

 

 



На лекциях мы проходили разные классы информационных систем, и поначалу было непонятно, куда отнести наш сайт. Я для себя сделал простое сравнение — не как в учебнике для аспирантов, а чтобы объяснить на защите, чем наш проект отличается от интернет‑магазина или от учётной системы на складе.

Сайт администрации — это не система учёта товаров: здесь нет корзины и оплаты. Это не чисто справочник вроде энциклопедии, потому что гражданин не только читает, но и отправляет обращение, а сотрудник меняет статус. Это и не просто «форум», потому что ответ официальный и его нужно хранить вместе с датой и исполнителем.

Ближе всего наш проект к сервисной информационной системе: есть регламент (подали → рассмотрели → ответили), есть роли, есть отчётность (аналитика). Плюс добавляется публикация информации (новости, документы) — поэтому в отчёте я писал, что система совмещает несколько функций.

Если сравнить с курсовыми работами одногруппников (CRM, склад), у нас больше внимания к доступности (режим для слабовидящих) и к иерархическому справочнику проблем — без него аналитика «по темам» не работает. Это я понял, когда строил график «топ категорий», а у части тестовых обращений категория в базе была пустой.



1.4. Обоснование выбора программных средств для реализации проекта 

При выборе технологического стека учитывались требования: безопасность, предсказуемость, возможность быстрого расширения, удобство разработки и сопровождения, совместимость с типовыми хостинг‑средами. 

В качестве серверной платформы используется PHP и фреймворк Laravel, поскольку: 

— Laravel предоставляет зрелую реализацию архитектуры MVC и стандартные механизмы маршрутизации; 

— присутствуют готовые решения для аутентификации/авторизации, middleware, CSRF‑защиты; 

— миграции позволяют управлять схемой БД, обеспечивая воспроизводимость развертывания; 

— ORM (Eloquent) упрощает работу с данными, описывает связи сущностей и уменьшает риск ошибок в SQL; 

— экосистема Laravel широко распространена, что облегчает поддержку и развитие проекта. 

Для хранения данных используется MySQL (или совместимая СУБД), что обусловлено: 

— распространённостью и стабильностью; 

— поддержкой транзакций и ограничений целостности; 

— эффективной работой со связями и агрегирующими запросами (необходимыми для аналитики). 

Для интерфейса используются: 

— Blade как шаблонизатор (с компонентами и секциями для переиспользования макета); 

— HTML/CSS/JavaScript для реализации адаптивной навигации, карусели, форм и виджета доступности; 

— Chart.js (подключение через CDN) для построения диаграмм в аналитическом модуле. 

Такой выбор обеспечивает достаточную функциональность без усложнения инфраструктуры и соответствует стилю официального сайта, где важны предсказуемость и стабильность. 

На втором–третьем курсе мы писали небольшие сайты на чистом PHP с подключением mysqli вручную. Это помогает понять основы, но для большого проекта с ролями, формами и файлами код быстро превращается в «спагетти»: много `include`, сложно искать ошибки, легко забыть про безопасность.

Laravel я уже видел на курсовом проекте, поэтому для практики логично было продолжить на том же стеке. Для меня главные плюсы такие:

— **Маршруты в одном файле** (`routes/web.php`) — видно, какая страница за что отвечает и какие middleware стоят;

— **Eloquent** — связи `belongsTo` / `hasMany` для обращений и справочников читаются проще, чем длинные SQL вручную;

— **Blade** — шапка и подвал подключаются один раз, не копируются на каждую страницу;

— **Встроенная авторизация и CSRF** — не нужно изобретать сессии с нуля;

— **Миграции** — можно поднять базу на другом компьютере командами `migrate` и `db:seed`.

Минусы тоже есть: проект «тяжелее», нужно понимать структуру папок, иногда непонятны сообщения об ошибках в логе. Но для учебного муниципального портала это, на мой взгляд, оправданный выбор. Альтернатива в виде WordPress подошла бы скорее для простого блога, а не для кастомной аналитики и иерархии проблем.

MySQL выбрал потому что на хостингах он распространён, а в колледже на лабораторных работах тоже использовали MySQL — не пришлось осваивать новую СУБД с нуля. Chart.js подключил через CDN для графиков аналитики: так быстрее, чем собирать графики вручную на canvas.

 

На практике архитектурные преимущества Laravel дополнительно важны для достижения требований по безопасности и сопровождаемости. Маршруты и контроллеры разделяются по назначению (публичный контур, пользовательский контур, служебные кабинеты), а доступ к действиям ограничивается на основе ролей. Для входных форм применяется серверная валидация, что позволяет гарантировать корректность данных до их сохранения. Для работы с файловыми вложениями используется контролируемое хранение и ограничение типов/размеров, чтобы снизить риск некорректных загрузок. 

Отдельно стоит отметить механизм воспроизводимости справочников: структура таблиц задаётся миграциями, а стартовые данные для иерархии категорий и проблем загружаются сидерами. Это важно при демонстрации работоспособности системы и при последующих итерациях развития проекта. 

С точки зрения безопасности и корректной эксплуатации в системе также предусматривается: 

— защита пользовательских сессий и хранение паролей в зашифрованном виде (пароли не хранятся в открытом виде, а механизм хэширования выбирается фреймворком и поддерживается в актуальном состоянии); 

— контроль доступа через роль/политики: гостям недоступны действия по созданию и редактированию обращений, сотрудникам доступны только служебные сценарии, администраторам — управление пользователями и справочниками; 

— защита от типовых веб‑атак уровня формы: применение CSRF‑токенов, проверка входных параметров, серверная валидация и нормализация данных; 

— обработка загрузок: использование ограничений MIME‑типа и расширений, контроль размера файла, сохранение вложений в изолированное файловое хранилище и запрет прямого выполнения загруженных данных; 

— журналирование событий (создание обращения, изменение статуса, фиксация ответа) — в дальнейшем это позволяет анализировать корректность работы сценариев и упрощает разбор инцидентов. 

Применяются типовые инструменты: 

— IDE/редактор кода (поддержка PHP, шаблонов, форматирования); 

— система контроля версий Git для управления изменениями; 

— встроенные инструменты Laravel (artisan) для миграций и обслуживания проекта. 

 

 

 

 

 

1.5. Постановка задачи  

Целью разработки является создание официального веб‑сайта администрации с расширением функционала за счёт модулей: 

— приём и сопровождение обращений граждан; 

— служебная обработка обращений сотрудниками; 

— аналитическая отчётность по обращениям. 

Функциональные требования: 

ФР‑1. Публичная часть сайта 

— публикация новостей и материалов по секциям; 

— страницы с документами и справочными материалами; 

— единое меню и структурированная навигация. 

ФР‑2. Управление информационным контентом 

— администратор должен иметь возможность создавать, редактировать и публиковать новости/статьи, которые отображаются в публичных блоках (в том числе на главной странице); 

— администратор должен иметь возможность формировать и редактировать разделы документов и справочной информации, включая прикрепление файлов и обновление карточек материалов; 

— администратор должен управлять элементами главной карусели (изображения и текстовые объявления), обеспечивая корректную публикацию и актуальность визуальных материалов; 

— в процессе редактирования система должна обеспечивать валидацию входных данных и корректную обработку загрузок (файлы/изображения), чтобы публичная часть сайта оставалась стабильной и доступной. 

ФР‑3. Регистрация и аутентификация 

— регистрация пользователя с созданием учётной записи; 

— вход/выход из системы; 

— защита от CSRF и корректная обработка ошибок. 

 

ФР‑4. Подача обращения гражданина 

Система должна предоставлять форму обращения, включающую: 

— обязательные поля: ФИО, email, текст обращения; 

— необязательные поля: телефон, почтовый адрес; 

— выбор классификации проблемы по справочнику (категория → подкатегория → детальная проблема); 

— возможность прикрепления файла; 

— обязательное согласие на обработку персональных данных. 

При проектировании формы обращений учитывается, что пользовательский ввод должен быть структурирован и проверяем. Для этого предусмотрены следующие принципы: 

— поля, обязательные для отправки, валидируются на сервере и отображаются пользователю с понятной логикой ошибок (например, “поле обязательно”, “некорректный формат”, “превышена допустимая длина”); 

— контактные данные нормализуются (в первую очередь email), чтобы исключить некорректные записи и обеспечить последующую доставку уведомлений и результатов рассмотрения; 

— иерархическая классификация проблемы выбирается из справочников и не должна позволять пользователю “обойти” зависимость уровней. На практике это реализуется через каскадный выбор: при выборе категории интерфейс показывает только соответствующие подкатегории, а при выборе подкатегории — доступные детальные проблемы; 

— вложения проверяются по типу и размеру до сохранения, чтобы минимизировать нагрузку на хранилище и снизить риск появления некорректных данных. 

Кроме того, допускается сценарий редактирования обращения только до момента ответа. После фактического подтверждения рассмотрения обращение переводится в “замороженное” состояние: пользователь видит итоговые сведения, но система предотвращает изменение существенного содержимого. Такой подход обеспечивает юридически значимую фиксацию текста и повышает воспроизводимость аналитики по историческим периодам. 

ФР‑5. Управление обращениями со стороны гражданина 

— просмотр списка своих обращений; 

— просмотр карточки обращения; 

— редактирование обращения только до момента ответа. 

ФР‑6. Обработка обращений сотрудником 

— просмотр списка обращений; 

— просмотр карточки обращения; 

— формирование ответа и фиксация даты ответа/исполнителя; 

— возможность добавления материалов к ответу (при необходимости). 

С точки зрения сценария работы сотрудника важным является согласованный интерфейс карточки обращения. Карточка должна отображать введённые гражданином реквизиты и текст обращения в исходном виде, классификацию проблемы (категория/подкатегория/деталь), контактные сведения для дальнейшей коммуникации, а также текущий статус и историю его изменений. Такое представление уменьшает риск ошибок при подготовке ответа и ускоряет прохождение этапов рассмотрения. 

После подготовки ответа сотрудник фиксирует результат и обновляет статус. С момента фиксации гражданин должен иметь возможность увидеть ответ и связанные с ним материалы (включая фотографии ответа, если предусмотрено проектом). Если используются вложения к ответу, они должны быть привязаны к конкретному обращению и корректно отображаться в карточке, чтобы пользователь мог сопоставить выводы с доказательной базой. 

ФР‑7. Справочники проблем 

— администратор должен управлять справочниками категорий проблем; 

— поддержка иерархии: категория → подкатегория → детальная проблема; 

— атрибуты активности и порядка сортировки; 

— использование справочника в пользовательских формах и в аналитике. 

Справочники проблем в системе выполняют роль управляемой семантики обращения. Иерархическая структура необходима, чтобы обеспечить: 

— сопоставимость данных для аналитики (одни и те же темы сопоставляются с одинаковыми справочными значениями); 

— контролируемость пользовательского выбора (гражданину предоставляется только актуальный набор значений); 

— корректность каскадных зависимостей: при деактивации элемента верхнего уровня связанные дочерние элементы не должны быть доступны для выбора, а существующие обращения должны сохранять ссылку на исторические значения. 

Таким образом, CRUD‑операции администратора должны сопровождаться проверками целостности. Это особенно важно при обновлении словаря проблем, когда система должна предотвращать появление “осиротевших” записей и гарантировать непротиворечивость связей между уровнями. 

ФР‑8. Аналитика 

Система должна предоставлять страницу аналитики, включающую: 

 

— KPI‑показатели по входящим обращениям и антикоррупционным сообщениям; 

— динамику по месяцам; 

— топ‑категории/подкатегории/детали проблем; 

— показатели SLA (вовремя/просрочено) и среднее время ответа. 

Аналитический модуль должен обеспечивать возможность интерпретации результатов без длительной подготовки со стороны сотрудника. Поэтому каждая группа показателей опирается на единые определения и вычисления: 

— KPI суммируют обращения по выбранным диапазонам дат и статусам, что позволяет оценивать текущую нагрузку; 

— динамика строится в календарной логике и отображает изменение числа обращений по месяцам, помогая выявлять пики и сезонные эффекты; 

— разделение на “топ‑категории” и “топ‑детали” позволяет обнаруживать повторяющиеся темы, требующие организационных решений; 

Для воспроизводимости аналитики используются агрегированные данные, полученные на основе истории статусов и временных меток. Тогда диаграммы “вовремя/просрочено” и графики динамики формируются одинаково при повторном расчёте для одного и того же набора данных. 

ФР‑9. Управление справочником проблем 

— система должна обеспечивать администратору интерфейс управления справочником категорий проблем, включающим уровни “категория → подкатегория → детальная проблема”; 

— для каждого элемента справочника должны поддерживаться признаки активности (включено/выключено), текстовые атрибуты и порядок отображения; 

— иерархические связи должны обеспечивать консистентность: подкатегория не может существовать без родительской категории, а детальная проблема — без соответствующей подкатегории. 

ФР‑10. Формирование и сохранение иерархии проблемы в обращении 

— при подаче обращения гражданин выбирает классификацию проблемы через последовательный выбор: категория → подкатегория → детальная проблема; 

— выбранные значения должны сохраняться в обращении как ссылки на справочные сущности и использоваться при построении аналитики; 

— изменение классификации должно учитывать регламент жизненного цикла обращения (например, допускается до момента ответа). 

ФР‑11. Вложения к обращению и материалы ответа 

— система должна позволять прикреплять к обращению файлы установленных форматов (PDF/DOC/DOCX/XLS/XLSX/JPG/PNG и др.) в пределах ограничений по размеру; 

— система должна предусматривать возможность прикрепления фотографий (и/или иных материалов) к ответу по обращению для повышения доказательности и информативности; 

— каждое вложение должно быть связано с конкретным обращением и/или конкретным ответом и корректно отображаться в карточке обращения. 

ФР‑12. Сценарий рассмотрения обращения сотрудником 

— сотрудник должен иметь возможность просматривать карточку обращения с отображением реквизитов и вложений; 

— сотрудник формирует ответ (текстовый результат) и фиксирует факт рассмотрения с обновлением статуса; 

— при необходимости для внутреннего управления формируется расписание/план обработки обращения, что повышает прозрачность сроков. 

ФР‑13. Служебная аналитика и контроль качества 

— система должна предоставлять страницы служебной аналитики, предназначенные для сотрудников и администраторов; 

— аналитика должна отображать показатели по статусам обращений и структуре тем на основе иерархии проблем; 

Таким образом, требования охватывают как пользовательский сценарий подачи обращения, так и внутренние регламентированные процессы рассмотрения, управления справочниками и формирования аналитических результатов. 

В рамках постановки задачи также детализируются входные и выходные данные, используемые при обработке обращений и расчёте аналитики. 

Входная информация (для обращения гражданина): 

— идентификационные сведения заявителя: фамилия, имя, отчество (ФИО); 

— контактные данные: адрес электронной почты (обязателен), а также телефон и почтовый адрес при необходимости; 

— текст обращения и его параметры (ограничение по длине и требования к корректности текста); 

— структурированная классификация проблемы: выбор категории, подкатегории и детальной проблемы из справочников; 

— вложение к обращению (по требованиям к типу/размеру файла) и факт согласия на обработку персональных данных. 

Входная информация (для сотрудника): 

— карточка обращения в унифицированном виде, включая реквизиты, классификацию проблемы, вложения и историю статусов; 

— условия формирования ответа (например, наличие/отсутствие дополнительных материалов, привязка фотографий к ответу, необходимость подготовки пояснений). 

Выходная информация (для гражданина): 

— отображение текущего статуса обращения (“на рассмотрении”, “ответ получен” и промежуточные статусы при их наличии); 

— доступ к ответу и материалам, прикреплённым к ответу, включая фотографии ответа; 

— прозрачность результата: гражданин видит дату ответа и, при необходимости, сведения об исполнителе. 

Выходная информация (для сотрудника и администратора): 

— список обращений в служебном контуре, отфильтрованный по статусам и классификации проблемы; 

— показатели качества обработки и контроль SLA; 

— аналитические срезы по структуре тем и динамике по месяцам. 

Такая детализация необходима, потому что аналитический контур должен быть воспроизводимым: при одинаковых данных система должна давать одинаковый результат расчёта. При расширении проекта (например, добавлении территориальной привязки) методика SLA остаётся инвариантной, меняются только измерения разрезов (по муниципальным зонам, улицам, учреждениям или тематическим признакам). 

Нефункциональные требования: 

НФР‑1. Доступность 

— наличие режима для слабовидящих; 

— поддержка увеличения шрифта; 

— контрастные схемы отображения; 

— заметный фокус для навигации с клавиатуры; 

— возможность отключения анимаций. 

Техническая сущность доступности в проекте заключается в том, что элементы интерфейса должны сохранять смысл и функциональность при любом режиме визуального отображения. Это достигается за счёт: 

— использования текстовых подписей и логически связанных меток для элементов форм (поля ввода, селекты, чек‑боксы), чтобы пользователь мог уверенно воспринимать контекст при использовании вспомогательных средств чтения; 

— гарантии видимого фокуса и предсказуемой последовательности переходов по элементам при навигации с клавиатуры; 

— поддержки режимов контраста без изменения сетки: интерфейс не должен “ломаться”, а элементы не должны терять читаемость из—за недостаточного цветового контраста; 

— реализации ошибок валидации как комбинации текста и подсветки поля, чтобы информация воспринималась независимо от восприятия цветов. 

НФР‑2. Безопасность 

— разграничение доступа по ролям; 

— защита персональных данных; 

— валидация пользовательского ввода; 

— ограничение типов и размеров загружаемых файлов. 

В контексте безопасности система должна учитывать типовые сценарии злоупотреблений: подмену данных на клиенте, попытки отправки некорректных параметров, загрузку файлов нестандартных типов и попытки доступа к служебной информации без авторизации. Поэтому безопасность реализуется в нескольких слоях: 

— защита сеансов и проверка подлинности запросов в приложении (CSRF‑подходы фреймворка); 

— серверная валидация всех входных полей формы и обработка ошибок таким образом, чтобы не раскрывать лишнюю техническую информацию; 

— контроль загрузок: проверка MIME/расширения, ограничение размера, изоляция файлового хранилища и предотвращение потенциально исполняемых данных; 

— ограничение доступа в служебной части системы только для ролей, которым разрешено создание/обработка/просмотр материалов. 

При реализации удобства и единообразия учитывается, что пользователь работает с системой в разных ролях и на разных устройствах. Для гостя ключевым становится понимание пути к целевому действию (например, “перейти к обращению”), для гражданина — простота заполнения формы и информативность сообщений об успешной отправке или ошибках валидации, а для сотрудника — удобство чтения карточки обращения и минимизация действий при формировании ответа. Поэтому интерфейс проектируется как набор повторно используемых компонентов (кнопки, формы, табличные/карточные списки, элементы статусов), которые наследуют тему округа и настройки доступности. 

Отдельное требование относится к согласованности поведения элементов. Например, модальные окна и уведомления должны следовать единому шаблону: один и тот же цвет/тип элемента должен обозначать аналогичное действие или состояние (успех, предупреждение, ошибка). Такой подход уменьшает когнитивную нагрузку и ускоряет обучение пользователя, что критично в административных процессах, где важна скорость обработки обращений. 

НФР‑4. Расширяемость 

— возможность добавления новых разделов контента; 

— возможность расширения аналитики до территориальной привязки.

2.1. Проектирование архитектуры информационного ресурса (диаграммы, схема данных) 

Архитектура — это, по сути, ответ на вопрос: из каких частей состоит система и как эти части обмениваются данными. Для студента 4 курса по специальности «Информационные системы и программирование» важно не только нарисовать красивую схему, но и объяснить её словами: зачем выбран клиент‑сервер, почему используется MVC, где хранятся файлы картинок и почему обращения граждан нельзя хранить «просто в папке на диске» без базы данных.

 

В основе информационного ресурса лежит классическая клиент‑серверная схема. С одной стороны находится пользователь с браузером (клиент), с другой — сервер, на котором работает программа на PHP (фреймворк Laravel). Между ними идёт обмен по протоколу HTTP или HTTPS: браузер отправляет запрос (например, «открыть главную страницу» или «отправить форму обращения»), сервер обрабатывает запрос и возвращает ответ — чаще всего HTML‑страницу, которую браузер показывает на экране.

На этапе разработки и демонстрации проекта я использовал встроенный сервер Laravel (команда `php artisan serve`). На реальном хостинге обычно ставят Apache или Nginx, но для учебного проекта важно, что логика приложения не меняется: меняется только «обёртка» веб‑сервера, а маршруты, контроллеры и модели остаются теми же.

Отдельно на схеме выделяется сервер базы данных MySQL. В нём хранятся таблицы: пользователи, роли, статьи, обращения, справочники категорий проблем и т.д. Файлы (фотографии к карусели, вложения к обращениям) в таблицу не записываются целиком — в базе хранится путь к файлу, а сам файл лежит в каталоге `storage/app/public`, который доступен через ссылку `public/storage` после команды `php artisan storage:link`. На практике с этим местом у меня как раз и возникла типичная «учебная» ошибка: картинки загружались, но не отображались, пока не была создана символическая ссылка. Это хороший пример того, что архитектура — не только диаграмма, но и правильная настройка окружения.

Для построения приложения выбран архитектурный подход MVC (Model — View — Controller). Его изучают на профильных дисциплинах, и в Laravel он реализован «из коробки», поэтому для дипломного и курсового проекта это было логичное решение.

Модель (Model) — это классы в папке `app/Models`, которые описывают данные и связи между таблицами. Например, модель `Appeal` описывает обращение гражданина, модель `Article` — новость или статью в разделе, модель `User` — учётную запись. Через модель удобно получать данные из MySQL без написания длинных SQL‑запросов вручную (используется ORM Eloquent).

Представление (View) — это шаблоны Blade в `resources/views`. Они определяют, как выглядит страница: где заголовок, где форма, где список новостей. В шаблон подставляются переменные, которые передал контроллер (например, список последних новостей на главной).

Контроллер (Controller) — классы в `app/Http/Controllers`, которые принимают запрос, проверяют права пользователя, вызывают модель, готовят данные и возвращают нужный шаблон или перенаправление на другую страницу.

Типовой путь запроса можно описать так:

1) пользователь нажимает ссылку или отправляет форму;

2) запрос попадает в файл маршрутов `routes/web.php`, где указано, какой контроллер и какой метод должны сработать;

3) перед контроллером могут выполниться middleware (промежуточные проверки): например, «пользователь должен быть авторизован» или «доступ только для администратора»;

4) контроллер обращается к модели, та читает или записывает данные в MySQL;

5) контроллер передаёт результат в Blade‑шаблон;

6) сервер отдаёт готовую HTML‑страницу в браузер.

Для формы обращения дополнительно используется небольшой API‑контроллер `ProblemCatalogController`: при выборе категории проблемы браузер запрашивает с сервера список подкатегорий и детальных проблем. Это сделано через JavaScript (fetch), чтобы не перезагружать всю страницу каждый раз. С точки зрения архитектуры это отдельный короткий канал обмена данными в формате JSON, хотя основной сайт всё равно строится как серверный рендеринг страниц, а не как отдельное одностраничное приложение.

Вывод по подразделу: клиент‑серверная модель и MVC позволяют разделить интерфейс, логику и данные. Для информационного ресурса муниципалитета это удобно, потому что публичная часть и служебная часть используют одну базу, но разные контроллеры и разные шаблоны.

 

Проектирование базы данных — один из самых ответственных этапов. Если таблицы спроектированы неудачно, потом сложно делать отчёты, фильтры и аналитику. В рамках практики я ориентировался на требования из главы 1: нужно хранить пользователей с ролями, контент (новости, карусель), обращения с классификацией, ответы сотрудников, антикоррупционные сообщения, справочники.

Ниже перечислены основные сущности и связи, которые должны быть отражены на ER‑диаграмме (рисунок 2.2).

Таблица `roles` — роли в системе (пользователь, сотрудник, администратор). Таблица `users` связана с `roles` связью «многие к одному»: у каждого пользователя одна роль, но одна роль может быть у многих пользователей.

Таблица `article_sections` — разделы статей (новости, финансы, информация и др.). Таблица `articles` хранит заголовок, текст, slug (адрес для URL), дату публикации, изображение, ссылку на раздел и на пользователя, который создал или редактировал материал. Таблица `article_files` — файлы, прикреплённые к статье.

Таблица `carousel_slides` — слайды для главной карусели: путь к изображению и порядок сортировки. Это отдельная сущность, потому что карусель не всегда совпадает с новостями: на главной могут быть объявления без отдельной статьи.

Таблица `appeals` — обращения граждан. Важные поля: ФИО, email, телефон, адрес, текст обращения, путь к вложению, согласие на обработку персональных данных, ссылки на `user_id` и на три уровня классификации (`problem_category_id`, `problem_subcategory_id`, `problem_detail_id`). Также есть поля для ответа сотрудника: текст ответа, дата ответа, кто ответил (`responded_by`).

Таблица `appeal_response_photos` — дополнительные фотографии к ответу (если сотрудник прикрепил несколько файлов). Связь «многие к одному» с `appeals`.

Таблица `anticorruption_reports` — антикоррупционные сообщения, по структуре похожие на обращения, но выделены в отдельную сущность, как того требует тематика раздела сайта.

Справочник проблем строится в три уровня:

— `problem_categories` (категория);

— `problem_subcategories` (подкатегория, ссылается на категорию);

— `problem_details` (детальная проблема, ссылается на подкатегорию).

Такая иерархия нужна, чтобы гражданин не писал свободный текст «наугад», а выбирал тему из списка. Тогда аналитика по обращениям становится осмысленной: можно посчитать, сколько обращений по дорогам, по ЖКХ, по благоустройству и т.д.

Кроме перечисленного, в проекте есть таблицы для блока «Администрация» (глава, заместители, подразделения, территории), вакансий, справочной информации (участковые, управляющие компании, экстренные телефоны), почётных граждан, депутатов. Они относятся к информационному наполнению сайта и тоже должны быть показаны на полной ER‑диаграмме, даже если в отчёте подробнее разобраны именно обращения.

Целостность данных обеспечивается внешними ключами в миграциях Laravel. Это значит, что нельзя случайно удалить категорию, на которую уже ссылаются обращения, без специальной настройки (обычно используют ограничения или логическое «отключение» записи в справочнике, а не физическое удаление).

Отдельно от таблиц на схеме стоит показать файловое хранилище: каталоги `articles`, `carousel`, `appeals` внутри `storage/app/public`. В ER‑диаграмме файлы часто не рисуют, но в пояснительной записке нужно прямо написать: в БД — путь, на диске — сам файл.

Вывод по подразделу: схема данных спроектирована под все основные контуры сайта. Связи между таблицами позволяют строить списки, карточки обращений и аналитические отчёты без дублирования информации в разных местах.

 

Диаграмма последовательности показывает, кто и в каком порядке «общается» при выполнении одного сценария. Для обращений граждан этот сценарий является центральным, поэтому он вынесен отдельно.

Рисунок 2.3 — Диаграмма последовательности действий при подаче обращения 

[Место для рисунка 2.3] 

Участники (объекты на диаграмме): Гражданин (пользователь), Браузер, Сервер (Laravel), База данных MySQL, Файловое хранилище. Иногда на диаграмме отдельно показывают «Форма обращения» как границу интерфейса — это допустимо, если так требует методичка.

Пошаговое описание сценария:

Шаг 1. Гражданин открывает сайт и входит в систему (логин и пароль). Без входа подать обращение нельзя — это сделано специально, чтобы была учётная запись и меньше спама. На диаграмме это отдельные сообщения: «ввести учётные данные», «проверить пароль», «создать сессию».

Шаг 2. Пользователь переходит на главную страницу или в раздел «Обращения граждан». Сервер через `HomeController` или `AppealController` отдаёт страницу с формой. Если пользователь не авторизован, его перенаправят на страницу входа — на диаграмме это можно показать как альтернативную ветку.

Шаг 3. При открытии формы браузер загружает список категорий проблем (верхний уровень справочника). Запрос идёт к `ProblemCatalogController`, ответ приходит в JSON, JavaScript заполняет первый выпадающий список.

Шаг 4. Пользователь выбирает категорию — браузер запрашивает подкатегории; выбирает подкатегорию — запрашивает детальные проблемы. Так реализована каскадная форма. На диаграмме это несколько коротких запросов «get subcategories» / «get details» между браузером и сервером.

Шаг 5. Пользователь заполняет ФИО, email, при необходимости телефон и адрес, вводит текст обращения, прикрепляет файл, ставит галочку согласия на обработку персональных данных. Нажимает «Отправить».

Шаг 6. Браузер отправляет POST‑запрос на маршрут сохранения обращения. Сервер в `AppealController::store` выполняет валидацию: проверяет обязательные поля, формат email, размер и тип файла, наличие согласия. Если есть ошибки — возвращает страницу с сообщениями, сценарий на диаграмме идёт в ветку «ошибка валидации».

Шаг 7. При успешной валидации сервер сохраняет файл вложения в `storage/app/public/appeals` (или аналогичный каталог), записывает путь в поле `attachment`, создаёт запись в таблице `appeals` со ссылками на пользователя и выбранную классификацию. В MySQL выполняется INSERT.

Шаг 8. Пользователь получает перенаправление на список «Мои обращения» с сообщением об успешной отправке. Статус обращения на этом этапе — «на рассмотрении» (логика статуса реализована в модели: если нет даты ответа, считается, что ответ ещё не дан).

Шаг 9. Сотрудник в служебном кабинете видит новое обращение в списке. Дальнейшие шаги (ответ, смена статуса) можно показать отдельной диаграммой или продолжением — в зависимости от требований к объёму. Для практики достаточно зафиксировать, что после шага 8 обращение доступно в контуре staff.

При оформлении рисунка 2.3 важно подписать стрелки: сплошная — вызов, пунктир — ответ. Нумерация сообщений облегчает защиту отчёта: преподаватель может спросить «что происходит на шаге 6», и ответ уже есть в тексте.

 

Диаграмма прецедентов (use case) показывает, что вообще может делать система и кто именно это делает. Она не уходит в технические детали вроде названий таблиц, зато хорошо демонстрирует границы системы.

На диаграмме выделяются акторы (действующие лица):

— Гость — человек, который просто зашёл на сайт без регистрации. Может читать новости, документы, справочную, смотреть разделы администрации, экологии и т.д. Не может подать обращение.

Прецеденты для гражданина: «Подать обращение», «Прикрепить файл к обращению», «Просмотреть список своих обращений», «Открыть карточку обращения», «Редактировать обращение (до ответа)», «Подать антикоррупционное сообщение», «Изменить пароль».

Логика процесса описывается так. Сотрудник открывает список обращений и выбирает новое (статус «на рассмотрении»). Далее открывается карточка: проверяются данные гражданина, текст, вложение, выбранная категория проблемы. Если информации недостаточно, в реальной практике сотрудник может связаться с заявителем по телефону или email — в системе это можно отразить комментарием в ответе, хотя отдельный модуль «звонков» в проекте не реализован.

На диаграмме это ветвление: «ответ заполнен?» — да → «обновить запись в БД» → «показать статус гражданину»; нет → возврат к редактированию.

Отдельная ветка: «просрочено по SLA» — если с момента создания прошло больше заданного числа дней (в проекте используется параметр, по умолчанию 7 дней), обращение попадает в просроченные в аналитике. Это не отдельный статус в карточке для гражданина, а вычисляемый показатель для руководства.

При построении диаграммы я старался не делать её слишком сложной: 10–15 элементов достаточно для отчёта по практике. Если преподаватель потребует больше деталей, можно добавить подпроцессы «согласование ответа» или «проверка вложения», но в текущей версии сайта они не выделены программно.

2.2. Разработка интерфейсов информационного ресурса 

Интерфейс — это то, что видит пользователь на экране. На практике я уделял этому много времени, потому что для официального сайта администрации важен не только «рабочий» функционал, но и внешний вид: сайт должен выглядеть солидно, быть читаемым и не пугать гражданина сложными формами.

При разработке интерфейса я исходил из фирменных требований округа: зелёная цветовая гамма, шрифты SK Posad и SK Posad Text, единая шапка и подвал. Одновременно нужно было сделать адаптивность (чтобы на телефоне тоже было удобно) и режим для слабовидящих — это отдельное требование, которое в обычных учебных лабораторных работах редко встречается, а здесь было в задании.

Общий макет всех страниц строится на файле `layouts/app.blade.php`. В нём подключаются шрифты, основные стили, шапка, подвал, виджет доступности и область для контента. Такой подход удобен: не нужно копировать один и тот же HTML на каждую страницу. Если изменить цвет кнопки в макете, он изменится везде.

Отдельно был введён класс `layout-constrain` с максимальной шириной 1200 пикселей и отступами по бокам. Это сделано потому, что на широком мониторе контент «разъезжался» к краям: карусель и кнопка «Режим для слабовидящих» выходили на всю ширину экрана, а основной текст — нет, и страница выглядела неровно. 2.3. Разработка клиентской части информационного ресурса 

Под клиентской частью в данном проекте понимается не отдельное React/Vue‑приложение, а всё, что формирует интерфейс в браузере: HTML‑разметка, CSS‑стили, JavaScript и шаблоны Blade, из которых сервер собирает страницу. Такой подход называют серверным рендерингом. Для официального информационного ресурса он подходит: страницы индексируются поисковиками проще, меньше «сложной» клиентской логики, проще сопровождать на обычном хостинге.

 

В Laravel представления лежат в `resources/views`. Я группировал их по смыслу, а не сваливал в одну папку — иначе через месяц сам бы запутался.

Основные группы:

— `layouts/` — общий каркас (`app.blade.php`);

— `components/` — повторяющиеся части (шапка `header.blade.php`, виджет доступности);

— `home.blade.php` — главная;

— `appeals/` — всё, что связано с обращениями (список, форма, просмотр, редактирование, partial формы);

— `articles/` — список и просмотр статей по разделам;

— `staff/` — служебные страницы для сотрудника;

— `admin/` — страницы администратора;

— отдельные blade‑файлы для документов, финансов, экологии, справочной, администрации и т.д.

Blade позволяет использовать наследование: `@extends('layouts.app')`, секции `@section('content')`, подключение `@include`. Например, форма обращения вынесена в `appeals/partials/form.blade.php`, чтобы не дублировать её на главной и в разделе обращений.

Чтобы было понятнее, как связаны глава 1 и реальный код, опишу форму обращения по шагам — так я сам объяснял себе логику при разработке.

Шаг 1. Пользователь открывает страницу с формой. Blade‑шаблон рисует HTML: поля ввода, три `<select>`, поле файла, чек‑бокс. В первый список категорий данные можно передать сразу с сервера (контроллер загружает активные категории из модели `ProblemCategory`).

Шаг 2. При изменении первого списка срабатывает JavaScript: отправляется запрос на API (например, `/api/problem-subcategories?category_id=...`). Сервер возвращает JSON со списком подкатегорий. Второй список заполняется без перезагрузки страницы.

Шаг 3. Аналогично для детальной проблемы при выборе подкатегории.

Шаг 4. Пользователь нажимает «Отправить». Браузер отправляет POST с CSRF‑токеном (Laravel добавляет его через `@csrf` в форме).

Шаг 5. `AppealController::store` проверяет поля: email обязателен, текст не пустой, согласие отмечено, файл — допустимого типа и размера. Если ошибка — возврат на форму с красными подсказками (стандартные сообщения валидации Blade).

Шаг 6. Если всё верно — файл сохраняется в `storage`, создаётся запись `Appeal`, пользователь перенаправляется на список обращений.

Этот сценарий я проверял много раз, потому что именно здесь чаще всего ломается логика: забытый CSRF, неправильное имя поля в форме, несовпадение имён в `validate` и в HTML. При тестировании я специально пробовал отправлять пустую форму и форму без галочки согласия — система должна не сохранять обращение, и так и происходит.

2.4. Разработка серверной части информационного ресурса 

Серверная часть — «двигатель» сайта. Именно здесь выполняются проверки, сохранение в базу, расчёт аналитики, разграничение прав. В проекте серверная часть построена на Laravel (актуальная версия в composer.json) и PHP 8.2.

 

Все маршруты веб‑интерфейса описаны в `routes/web.php`. Это центральный файл, по которому можно понять, какие URL что делают.

Публичные маршруты не требуют входа: главная, новости, документы, финансы, экология, справочная, страницы администрации как информация, регистрация и вход.

Маршруты с middleware `auth` доступны только авторизованным: обращения, профиль, скачивание своих вложений.

Группа `staff` с префиксом и middleware по роли — для сотрудников: статьи, карусель, обращения, аналитика.

Группа `admin` — для администраторов: дашборд, пользователи, справочник проблем.

Такое разделение я настраивал постепенно: сначала сделал обращения, потом добавил staff, потом admin. На практике важно было не перепутать middleware, иначе обычный пользователь мог бы теоретически открыть служебную страницу — middleware как раз это предотвращает.

Модели Eloquent избавляют от ручного написания `INSERT` и `SELECT` в каждом месте. Например, модель `Appeal` описывает связи:

`belongsTo` ProblemCategory, ProblemSubcategory, ProblemDetail — классификация;

`hasMany` AppealResponsePhoto — фото к ответу;

`belongsTo` User как responder — кто ответил.

В модели можно определить аксессоры: например, вычисляемый статус «на рассмотрении» / «ответ получен» по наличию `responded_at`. Тогда в blade достаточно вывести `$appeal->status_label`, не дублируя условия в шаблоне.

Модели `Article`, `CarouselSlide`, `User`, `Role` работают аналогично. Для статей важна связь с разделом (`article_section_id`) и slug для красивых URL.

**Проблема 1 — картинки не отображались.** Я загрузил изображения для карусели и новостей через админку, в базе пути были, а в браузере — пустой значок. Долго думал, что ошибка в Blade‑шаблоне. **Проблема 2 — карусель «вылезала» за края на мобильном.** Сначала я пытался сделать карусель на всю ширину экрана через отрицательные отступы (`margin-left: calc(50% - 50vw)`), как в примерах из интернета. **Проблема 3 — каскадные списки в форме обращения.** Пользователь выбирает категорию, потом подкатегорию, потом деталь. Ошибался с именами параметров в URL и с тем, что второй список не очищался при смене первого — пришлось дописать обнуление options в JS.

**Проблема 4 — валидация и сообщения об ошибках.** Laravel выдаёт ошибки автоматически, но тексты по умолчанию на английском или слишком общие. Я добавил русские сообщения в `validate(..., [...])` для пароля и обращений. На защите это показывает, что форма «дружелюбная» для гражданина.

**Проблема 5 — объём отчёта.** Требование — около 70 страниц в Word. Один только текст в markdown даёт меньше листов, чем кажется, потому что в Word добавляются титул, содержание, рисунки, таблицы, приложения с кодом. Поэтому в отчёте много мест под рисунки 2.1–2.25 и приложение Б — их обязательно нужно вставить при переносе в Word.

**Проблема 6 — нехватка времени на автотесты.** В курсе проходили PHPUnit, но на практике я успел в основном ручное тестирование по таблице 2.1. Для диплома хочу добавить хотя бы несколько feature‑тестов на подачу обращения и доступ к staff‑разделу.

Таким образом, цель практики достигнута: подготовлены материалы для диплома и создан работающий прототип информационного ресурса. Все поставленные задачи выполнены, о чём также свидетельствует дневник практики.

В процессе работы я закрепил навыки, которые изучались на курсе: проектирование БД, работа с фреймворком Laravel, вёрстка адаптивных страниц, основы тестирования. Отдельно отмечу, что на практике стало понятнее, как связаны между собой «красивая страница» и «правильная база»: если в форме нет нормальной классификации обращения, аналитика потом не получится, даже если графики нарисовать красиво.

В качестве дальнейшего развития проекта (уже на этапе диплома) можно выделить: привязку обращений к территориям и отображение «тепловой карты» проблем, расширение автоматических тестов, вывод сайта на хостинг с HTTPS, доработку мобильного интерфейса. Эти направления логично вытекают из текущей версии и не требуют полной переделки системы.

Материалы отчёта, приложений и скриншотов планирую использовать при защите преддипломной практики и при написании пояснительной записки к выпускной квалификационной работе.

<?php 

 

namespace App\Http\Controllers\Admin; 

 

use App\Http\Controllers\Controller; 

use App\Models\Role; 

use App\Models\User; 

use Illuminate\Http\Request; 

use Illuminate\Support\Facades\Hash; 

 

class UserController extends Controller 

{ 

    public function index() 

    { 

        $users = User::with('role')->paginate(15); 

        return view('admin.users.index', compact('users')); 

    } 

 

    public function edit(User $user) 

    { 

        $roles = Role::all(); 

        return view('admin.users.edit', compact('user', 'roles')); 

    } 

 

    public function update(Request $request, User $user) 

    { 

        $rules = [ 

            'name' => 'required|string|max:255', 

            'email' => 'required|email|unique:users,email,' . $user->id, 

            'role_id' => 'required|exists:roles,id', 

        ]; 

        if ($request->filled('password')) { 

            $rules['password'] = 'required|string|min:8|confirmed'; 

        } 

        $request->validate($rules, [ 

            'password.min' => 'Пароль должен быть не менее 8 символов.', 

            'password.confirmed' => 'Пароль и подтверждение не совпадают.', 

        ]); 

 

        $user->fill($request->only('name', 'email', 'role_id')); 

        if ($request->filled('password')) { 

            $user->password = $request->password; // cast 'hashed' on User model will hash it 

        } 

        $user->save(); 

 

        return redirect()->route('admin.users.index') 

            ->with('success', 'Пользователь успешно обновлен'); 

    } 

 

    public function create() 

    { 

        $roles = Role::all(); 

        return view('admin.users.create', compact('roles')); 

    } 

 

    public function store(Request $request) 

    { 

        $request->validate([ 

            'name' => 'required|string|max:255', 

            'email' => 'required|email|unique:users', 

            'password' => 'required|string|min:8', 

            'role_id' => 'required|exists:roles,id', 

        ]); 

 

        User::create([ 

            'name' => $request->name, 

            'email' => $request->email, 

            'password' => Hash::make($request->password), 

            'role_id' => $request->role_id, 

        ]); 

 

        return redirect()->route('admin.users.index') 

            ->with('success', 'Пользователь успешно создан'); 

    } 

 

    public function destroy(User $user) 

    { 

        if ($user->id === auth()->id()) { 

            return redirect()->route('admin.users.index') 

                ->with('error', 'Вы не можете удалить самого себя'); 

        } 

 

        $user->delete(); 

 

        return redirect()->route('admin.users.index') 

            ->with('success', 'Пользователь успешно удален'); 

    }
